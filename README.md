# 作品集网站重构 · 第一阶段开发文档

## 一、项目目标

将现有图片式作品集重构为代码驱动的现代化网站，实现可视化编辑、模块化管理、GitHub 存储及 CDN 加速。

第一阶段仅实现**一个首页及对应的中文管理后台**，不开发多页面管理功能。

## 二、技术架构

- 前端：Astro + React + TypeScript
- 样式：CSS Modules
- 可视化编辑器：Puck（官方版本）
- 界面语言：简体中文，使用官方 Dictionary API
- 内容存储：GitHub + JSON
- 管理接口：Cloudflare Workers
- 部署：Cloudflare Pages
- CDN：Cloudflare，预留 EdgeOne 接入能力

优先使用成熟、稳定的官方方案，减少不必要的第三方依赖。

## 三、页面开发

参考提供的作品集首页设计图，使用 HTML、CSS 和组件化方式高度还原。

要求：

1. 文字必须是真实文本，禁止将整张设计稿作为页面背景。
2. 支持加载用户提供的本地字体文件。
3. 网格、线条、背景、排版优先使用 CSS/SVG 实现。
4. 支持桌面与移动端响应式布局。
5. 页面采用静态生成，优先保证加载速度和视觉还原度。
6. 预留交互动效扩展能力。

## 四、模块化规范

所有页面内容基于独立组件构建。

- 每个模块具有唯一 ID、类型、版本及独立配置。
- 模块之间不得直接依赖内部样式和实现。
- 使用 CSS Modules 隔离样式，避免全局污染。
- 模块配置采用统一 JSON Schema。
- 通过模块注册表统一管理组件。
- 新增模块不得修改已有模块的数据结构。
- 已发布模块的破坏性修改必须通过新版本或数据迁移处理。
- 页面 JSON 与组件源码分离，编辑器只能修改配置，不直接修改源码。

首批只实现首页实际需要的模块，不提前开发无关组件。

## 五、可视化管理后台

集成官方 Puck 编辑器，后台路径为 `/admin`。

实现以下基础能力：

1. 简体中文操作界面。
2. 模块添加、删除、排序。
3. 编辑文字、图片、字体、颜色、间距等已开放属性。
4. 实时预览页面效果。
5. 桌面与移动端预览。
6. 保存草稿与发布页面。
7. 页面数据使用结构化 JSON 保存。

模块样式参数应合理限制，避免编辑操作破坏整体布局。

## 六、GitHub 与部署

- GitHub 作为唯一内容仓库。
- 页面配置、组件代码、图片及字体统一版本管理。
- Cloudflare Worker 负责鉴权和 GitHub API 操作。
- 使用 GitHub App 或最小权限凭证，密钥仅保存在服务端环境变量中。
- 草稿与已发布内容隔离，保存草稿不得触发正式网站更新。
- 发布后触发 Cloudflare Pages 自动构建。
- 支持通过 Git 历史记录回退。
- 禁止在前端暴露任何密钥。

开发阶段允许使用本地 JSON 保存，确保未配置 GitHub 凭证时也能运行和预览。

## 七、开发原则

1. 优先模块解耦和长期可维护性。
2. 不引入传统数据库及常驻服务器。
3. 不修改 Puck 官方源码，通过公开 API 扩展功能。
4. 避免过度设计，仅实现第一阶段必要功能。
5. 保持代码目录清晰，方便未来新增页面和组件。
6. 严格区分开发环境与正式环境。
7. 所有核心功能必须实际可运行，禁止使用假数据模拟已完成的保存或发布功能。

## 八、第一阶段验收标准

- 首页可以正常访问，并高度还原参考设计稿。
- 字体、文字、网格等元素均由代码实现。
- `/admin` 可以正常打开中文可视化编辑器。
- 能够修改首页模块并实时预览。
- 页面 JSON 可以保存、重新加载且内容一致。
- 已配置 GitHub 后，可以完成真实发布。
- 新增独立测试模块不会破坏原有模块。
- 网站可以通过 Cloudflare Pages 构建部署。

## 九、执行要求

首先检查现有项目结构及相关资源，制定最小可行的实施方案，再按模块逐步开发。

优先完成首页视觉还原和模块架构，其次实现 Puck 编辑器，最后集成 GitHub 发布流程。

不要一次性开发完整 CMS，也不要为了未来可能使用的功能增加不必要的复杂度。

## 十五、装修选图与素材命名

装修页继续使用 Puck 原生折叠数组列表，与“分类项目”相同：点击单项展开，拖动手柄排序，沿用原生删除操作。展开后依次为作品名称、选择文件夹、只读实际路径、是否动态；没有项目图片下拉框、缩略图面板、上移／下移按钮或可编辑路径。选择文件夹后自动识别封面和图层，实际路径仅用于查看和复制，长路径换行且不撑宽面板。

作品目录保留源项目全名，例如：

```text
public/images/works/
  260605_贴片_主号_哈根达斯&梦龙/
    贴片预览.jpg
    分层素材/（内部文件保留原名）
  250806_贴片_宠物生活_抢跑亚宠展/
    贴片预览.jpg
    动态预览/（原完整画布素材）
    分层素材/（原裁切素材）
  shared/（原共用主播、界面文件）
  catalog.json
```

不把项目名翻译成英文缩写。catalog 中的稳定内部 ID 用于保留详情 URL 和旧配置兼容，与文件系统名称分离；旧封面路径作为别名保留。`scripts/work-directories.py` 统一分配目录：同名不同作品保留完整原名并追加稳定短后缀，避免覆盖；已有作品复用已登记目录。

从电脑选择文件时，已有图片按内容识别回项目站内路径；新图片保留原始文件名，存入 `public/images/uploads/{内容哈希}/{原文件名}`。同名不同内容进入不同目录，重复内容复用已有文件，不覆盖。浏览器不提供文件原始绝对路径，配置仅保存 `/images/...`，不依赖电脑用户名或项目父目录。目录转换支持中文原名，源码以 public 为入口，不直接写 dist。

选图后使用“是否动态”控制静态图片或已关联作品的悬停与分层交互；素材关系仍以 `public/images/works/catalog.json` 为准，没有动画素材的普通图片不能发布为动态作品。

电脑文件导入由本机同源 `/api/assets` 提供，支持 JPG、PNG、WebP、GIF、AVIF，单图不超过 20 MB；线上可填写已发布素材路径，电脑文件导入在本地装修页使用。新增图片需随项目提交、构建后用于正式站点。

## 十六、按作品文件夹识别素材

贴片作品使用文件夹选择器，个人照片继续使用单张图片选择器。已有项目目录（包括 dist 中对应的副本）会按封面和资源内容识别、复用，不重复复制，也不保存电脑绝对路径。

新作品目录可采用以下规范：

1. 规范作品包：封面及 `作品.json`，其中记录相对素材路径、画布和图层坐标。构建会为当前已登记的作品生成该文件。
2. Photoshop 原始导出目录：`贴片预览.jpg/png`、原图层文件及同一目录的 `*_layout.json`。系统按真实导出坐标识别并导入。
3. 单图作品目录：只有一张图片时可作为静态作品；多图却没有坐标说明的目录会报错，不猜测分层位置。

本地 `/api/work-folders` 接收选择的文件内容和相对结构，保留源目录及文件名；同名不同内容使用稳定后缀区分。单目录最多 500 个支持的文件、150 MB。新作品导入时自动更新素材目录索引和校验器，装修页保留未保存的名称等编辑内容。导入不等于发布页面，仍需保存草稿或发布。

### 贴片作品排版

装修页“贴片设计作品 → 作品排版”可设置安全区域总宽度、单图宽度、单图高度和图间距，均以 1920 宽设计稿为单位随桌面画布等比缩放。安全区域居中，图片保持比例显示在统一尺寸内。间距为 0 时自动均分剩余空间：`（安全区域宽度 − 单图宽度 × 图片数量）÷（图片数量 − 1）`；正数为固定间距，整组居中；单张居中。空间不足时不缩小图片，安全区内横向滚动。手机继续两列。已有未设置排版的旧配置仍保留原布局。

### 页面轻吸附

页面滚动采用原生纵向 proximity 吸附，接近个人介绍、目录、贴片作品或结束页的页首时自动对齐；封面可回到顶部。开启 Photoshop 外壳时预留顶部工具栏高度，隐藏后对齐视口顶部。长内容中间仍可自由停留，快速滚动可跨过多页，不强制逐屏翻页；发布页和装修预览共用相同行为。
